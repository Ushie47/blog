Git — это распределённая система контроля версий, которая отслеживает 
изменения файлов проекта во времени, позволяя сохранять, сравнивать и 
восстанавливать разные версии. В этом проекте Git сыграл центральную 
роль в управлении сайтом и его развёртывании на GitHub Pages.

## Основные понятия

**Репозиторий.** Локальный репозиторий создаётся командой `git init`, 
после чего папка становится проектом с контролем версий. Это отдельный 
процесс от GitHub — репозиторий на GitHub появляется только после того, 
как к проекту явно подключают удалённый адрес и отправляют туда данные.

**Коммиты.** Каждый `git commit` фиксирует снимок изменений, добавленных 
командой `git add`, вместе с сообщением, описывающим суть изменений. Так 
формируется история проекта, к которой можно вернуться в любой момент.

**Ветки.** В современных версиях Git основная ветка по умолчанию 
называется `main` (в старых — `master`). Команда `git branch -M main` 
позволяет переименовать текущую ветку.

**Удалённые репозитории (remotes).** Команда `git remote add origin <url>` 
связывает локальный репозиторий с удалённым. Команда `git push` отправляет 
локальные коммиты на сервер, а `git pull` — забирает изменения обратно.

**Подмодули.** В этом проекте я использовал `git submodule add`, чтобы 
подключить тему оформления Hugo как отдельный Git-репозиторий внутри 
основного проекта — это позволяет отслеживать версию темы независимо 
от остального кода.

**Аутентификация.** GitHub больше не поддерживает вход по паролю для 
операций с Git через HTTPS. Вместо этого я настроил аутентификацию по 
SSH-ключу, что избавляет от повторного ввода данных при каждом push.

## Что я вынес из этой работы

Столкновение с реальными ошибками — неудачными push, несовпадением 
веток, сломанными подмодулями и проблемами с DNS в WSL — дало гораздо 
более ясное понимание того, как Git работает изнутри, а не просто 
запоминание команд. Главным открытием стало чёткое понимание разницы 
между локальным репозиторием и его удалённым аналогом на GitHub.
